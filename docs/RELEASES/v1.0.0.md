# Dodong OS v1.0.0

**Release date:** 2026-09-02
**Version source of truth:** `backend/config/__init__.py` (`__version__`)
**Deployment status:** `V1_RELEASE_READY_BUT_NOT_LIVE_DEPLOYED`

---

## Summary

Dodong OS v1.0 is the first release candidate of an AI-assisted CRM. It
provides deterministic CRM reads, four explicitly-confirmed CRM write
actions, deterministic background automation with an optional AI digest
summary, a read-first RAG / knowledge assistant, and a hardened production
configuration. The AI layer never touches the ORM directly and can never
perform an autonomous CRM write.

---

## Major capabilities

### CRM foundation
Leads, lead statuses (`new → contacted → qualified → proposal → won / lost`),
tasks (type/priority/status/due date), notes, and an activity timeline.
Pipeline and lead/task views over Bootstrap + HTMX.

### CRM Read Assistant (`/assistant/`)
Natural-language questions answered from deterministic CRM read tools:
priority / overdue / pending / lead tasks, lead lookup, lead search, lead
activities, pipeline summary. An AI provider only rephrases already-verified
tool results; if it fails, the deterministic answer is shown. Authenticated
users only.

### Controlled CRM write actions
Four actions, each gated by
`proposal → signed token → explicit Confirm → verified executor → CRM service → post-write verification → AIActionAudit`:

1. `create_lead_task`
2. `complete_lead_task`
3. `change_lead_status`
4. `add_lead_note`

Before confirmation the user sees the action, the affected lead/task, the
current state, the intended new state/content, and a clear "no CRM change
has been made yet" notice. Conversational phrases ("Yes", "Confirm", "Go
ahead", "Do it", "Complete it") never confirm. Every confirmed write is
audited and visible at `/assistant/audit/` (staff).

### Background automation
`python manage.py run_crm_checks` runs deterministic read-only checks
(due-soon tasks, stale leads), persists deduplicated findings to `CRMDigest`
(resolve/reopen semantics), and optionally produces an AI digest summary
with a deterministic fallback. Overlap protection + stale-run recovery via
`ScheduledCheckRun`. History and status at `/automation/runs/` (staff). The
automation path never invokes the confirmed-write executor.

### Knowledge / RAG (`/assistant/knowledge/`, staff)
Controlled ingestion of approved documents (`manual` / `internal_note`),
deterministic character-bounded chunking, deterministic lexical retrieval
(token-overlap ranking; **no embeddings / pgvector**), and a grounded answer
layer. Retrieved text is treated strictly as **data**; the prompt states
that any instructions inside a document must be ignored. Provider failure →
deterministic evidence-only answer. Document management is Django admin
(saving reindexes; a "Reindex selected" action is provided).

### Production hardening
`DJANGO_ENV=production` profile with env-driven `SECRET_KEY`, `ALLOWED_HOSTS`,
`CSRF_TRUSTED_ORIGINS`, `DATABASE_URL` (PostgreSQL, psycopg 3), and security
headers (SSL redirect, HSTS, secure cookies, nosniff, `X-Frame-Options
DENY`, `X-Forwarded-Proto`). Production refuses an insecure key, `DEBUG=True`,
empty hosts, or the SQLite fallback. WhiteNoise static, gunicorn, Dockerfile,
GitHub Actions CI (incl. an optional PostgreSQL smoke job), health
(`/health/` incl. version) and readiness (`/ready/`) endpoints, console
logging with no secret leakage, and centralized input limits
(`CRM_NOTE_MAX_LENGTH=5000`, `RAG_QUERY_MAX_CHARS=2000`,
`KNOWLEDGE_DOC_MAX_CHARS=200000`).

## Architecture & safety model

```
AI / RAG / automation orchestration
        ↓ (never the ORM directly)
Registered tools  /  CRM services  /  knowledge services
        ↓
Django ORM → PostgreSQL (production) / SQLite (development)
```

- The AI layer has **no direct ORM access** (architecture-tested).
- **No autonomous CRM writes.** Every write needs an explicit human Confirm
  with a valid signed proposal token.
- Signed proposal tokens: tamper-evident, 10-minute expiry, single-use
  (replay-protected), CSRF-protected, POST-only.
- RAG and automation are read-only and can never call the write executor.
- Retrieved knowledge is data, not instructions.
- The automated test suite (532 tests) makes **zero real external AI calls**.

---

## Supported vs. not supported

**Read:** CRM tasks / leads / pipeline / activities, knowledge retrieval,
automation findings & run history.

**Controlled write (explicit confirmation only):** create task, complete
task, change lead status, add lead note.

**Not supported in v1.0:** autonomous writes; deletes; bulk AI mutations;
automatic internet ingestion; arbitrary CRM ORM access from AI;
conversational confirmation; unrestricted agent tool execution.

## Known limitations (accepted, not blockers)

- RAG retrieval is lexical; **no pgvector / semantic embeddings** (deferred,
  contingent on the PostgreSQL deployment).
- Combined "CRM data + knowledge policy" questions are not auto-routed;
  issue the CRM read and the knowledge query separately.
- `get_stale_leads` evaluates its last-activity rule in Python over active
  leads (fine at current scale).
- `/automation/runs/` and `get_recent_check_runs` are capped at 50 with no
  pagination.
- No external "automation didn't run" / uptime alerting (candidate for a
  future release).
- No application-level rate limiting on the authenticated AI endpoints
  (small scale; no Redis).
- **PostgreSQL runtime not yet verified** from a developer machine — run the
  CI `postgres-smoke` job / a disposable-DB drill before first cutover.
- **Docker image not built locally** (no Docker daemon in the build
  environment); the `Dockerfile` is prepared.
- **Live Azure deployment not executed** (production account not available
  in this environment).
